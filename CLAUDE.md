# CLAUDE.md

Orientation for Claude Code sessions. Read this before searching the repo.
`README.md` has the long-form simulation/tuning docs; this file covers what
you need to work on the code, especially the hardware controller.

## What this project is

A PC-side controller for a 4-motor robotic arm (CubeMars AK-series motors),
built around a MuJoCo model of the arm. The PC does all computation; an STM32
(firmware **not** in this repo) is a serial-to-CAN bridge that forwards
MIT-mode commands (P, V, Kp, Kd, T) to the motors and streams encoder feedback
back. The MuJoCo viewer's **Control tab sliders** are the operator's position
input; the real arm follows the simulated reference.

Collaborators: Matt Mitchell and Andrea Basuroski both push to
`github.com/abasuroski/sim`. Pull before working on `main`.

## Running things (Windows)

All code lives in `Robosim/`. Use the project venv (global `python` is not
registered on this machine). MuJoCo 3.12.0, pyserial 3.5.

```powershell
& .\Robosim\.venv\Scripts\python.exe .\Robosim\hardware_integrated_main_controller.py COM5   # hardware
& .\Robosim\.venv\Scripts\python.exe .\Robosim\hardware_integrated_main_controller.py        # simulation only, no serial
```

Hardware workflow in the controller terminal: `a` enable motors -> `s` start
(snapshots encoders; nothing moves) -> drag Control-tab sliders, or
`g <j> <pos>` (`g 4 20deg`, `g 4 +0.1`), `h` home, `p`/`r` pause/resume,
`z` print encoders, `d` toggle command printout, `f` toggle telemetry, `q` quit.

There is no test suite. Verify changes by importing the module with the venv
python, and by headless MuJoCo scripts (load the model, set `qpos`, call
`mj_forward`, inspect the result). Real verification needs the arm.

## Motors and coordinates

| Motor | Joint | Motor model | Gear | Direction |
|---|---|---|---|---|
| M1 | `revolute_1` (base) | AK60 (`ak60_revolute_1`) | 1 | +1 |
| M2 | `revolute_2` (shoulder) | AK70 | 1 | +1 |
| M3 | `revolute_3` (elbow) | AK70 | 1 | +1 |
| M4 | `revolute_4` (linkage) | AK40 | 1.25 | -1 |

- **M4 is the tricky one.** Its MJCF actuator `ctrl` and the serial command are
  *motor-side*; `qpos` is *joint-side*. Joint = motor × `MOTOR_DIRECTION[4]` / 1.25.
  Gains convert as `k_motor = k_joint / gear²`.
- **Synchronization is relative, not absolute.** On `s`, the controller stores
  `_encoder_at_sync` and `_sim_at_sync`, plus `_pos_cmd_offset = encoder - ctrl`.
  The hardware then follows reference *changes*. A constant pose difference
  between sim and arm persists.
- **Passive four-bar linkage.** `revolute_5,6,7,8,9,13` (and the loop-closure
  joint `revolute_14_loop_closure`) move linearly with `revolute_4`. The MJCF
  joint equalities are `r5=-r4`, `r9=-r7`, `r6=-r8`, `r13=-r8`, `r14=-r8`, and
  a weld closes the loop. The resulting coupling, `r7=+r4` and `r8=-r4`, is
  encoded in `CONSTRAINED_JOINTS`, which sets followers kinematically as deltas
  from the keyframe. This coupling was verified against settled simulation to
  within 0.0025 rad.
  `revolute_12` is not coupled.
- At `hardware_zero`, `revolute_4` rests on its 1.552 rad joint limit (hard stop).

## Control loop (each tick)

1. Read feedback (`si.snapshot()`, lag-extrapolated).
2. Write the state into MuJoCo: encoders if `CLOSED_LOOP`, else the limiter reference. Then `mj_forward`.
3. `controller.update()` schedules gains; `limiter.update()` advances the reference from the sliders.
4. `_compute_tau_ff()` computes gravity feedforward (forced to 0 when `ZERO_TFF`).
5. `_CommandStreamer.send()` writes only changed P/V/K/D/T fields, plus a full frame per motor every 0.25 s keepalive.
6. Log one CSV row.

Current flags on `main`: `CLOSED_LOOP = True`, `ZERO_TFF = True`, `DEBUG_COMMANDS = True`.

## Known issues and history (read before touching feedforward or M4)

- **The STM32 disables a motor when its feedback age exceeds ~0.2 s** (a
  firmware watchdog; `WATCHDOG_AGE_S` in `plot_run_log.py` marks it on graphs).
  Serial overload causes this. At 115200 baud, full frames for 4 motors at 84 Hz
  (~18 kB/s) exceeded the ~11.5 kB/s capacity. The fix that made the arm work:
  1 Mbaud plus change-only command streaming. Keep traffic low.
- **The `mj_inverse` feedforward for M4 is wrong** whenever M4 leaves
  `hardware_zero`. Reading the `revolute_4` row of `qfrc_inverse` picks up the
  stiff loop-closure weld's reaction to kinematic residuals: hundreds of N·m
  instead of the real ~0.2 N·m (motor side). Clamped, it pushes M4 the wrong
  way. `main` avoids this with `ZERO_TFF = True`. A verified fix exists in
  commit `a0a7821` (branch `10_17_experiments`), but it is **not on `main`**.
  The fix:
  1. Add `"revolute_14_loop_closure": ("revolute_4", 1.0)` to `CONSTRAINED_JOINTS`.
  2. Compute feedforward by virtual work: `τ_j = Σ S_ij · (qfrc_bias − qfrc_passive)_i`
     over the driven DOF plus its followers, ignoring constraint forces. This
     matches settled-simulation ground truth within ~0.001 N·m for M4 and
     exactly for M1–M3.
  3. A limiter (`_limit_ak40_command_torque`) that reduces feedforward before
     PD and never zeroes Kp/Kd. `Kp=0, Kd=0` in MIT mode means a limp motor.
- M4 gains are soft (Kp ≈ 0.4 N·m/rad motor side), so unmodelled load causes
  noticeable steady-state error.
- In the logs, only M4 has reported feedback on some runs. Motors without
  feedback still get commands, using a sync offset that defaults to 0.
- The named-pipe input (`/tmp/robot_cmd`, `os.mkfifo`) only works on
  Linux/macOS. On Windows it prints "unavailable"; this is harmless.

## Conventions

- Match the existing style: type hints, `from __future__ import annotations`,
  explanatory comments on *why* (units, motor vs joint side), and `[ctrl]`/`[serial]` print prefixes.
- State units and side in names (`_motor_nm`, `_joint_rad`).
- Hardware safety matters. Prefer changes that fail limp-safe: no motion on
  start, clamp torque, and keep `0X` freeze on connect.
- Run logs are often committed with code changes. Commit them only if asked.
